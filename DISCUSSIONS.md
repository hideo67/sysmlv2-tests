# Discussions with the AI

This file is for recording the discussions done with AI.

## Motivation
I tried using opensysml for a project and noticed that the model I was using
surfaced a number of conformance issues of the API.  I guess that other similar
MDKs may not have enough variety of test cases, so I want to create one so that
I can assess the maturity of the options.

The set of problems that I happened to encounter was filed as issues at
https://github.com/Open-MBEE/OpenSysML/issues/ in the range issue 1956 to 1965,
1985 and 1986. So you can see the kind of problems that was encountered. I would
like this test case to probe this kind of level of detail.

## Step 1.
Clone the necessary repos. Create .gitignore and exclude the repo dirs. Assess
if required build tools are available on this OS and report anything that needs
to be installed. AI should not install tools on its own.

## Step 2 (first matrix, A10 part usages)
Matrix `test-suite/data/matrices/A10.md`, model `data/models/A10.sysml`, expected
values `data/cases/A10.json`, all generated by `data/gen_a10.py`. Shared by all
suites; each suite only implements an adapter per `check` kind. A test can end as
pass, fail, or unsupported (the API offers no way to read the property at all;
reported as skip). Results are CSVs in `test-suite/results/` (git-ignored);
`test-suite/run-all.sh [suite]` runs suites and `test-suite/report.py` tabulates.

Feedback applied: the matrix is the full cross product of what is read (name,
type, isComposite, isReference) x where the usage appears (package, part def,
read through a usage typed by the def) x kind (owned, ref), plus an unnamed-part
row per location: 27 cases. A member counts as FAIL if the API does not list it
as a member of the usage it is read through; UNSUPPORTED only if the property
cannot be read at all (this takes precedence).

Later addition: a fourth location, members of `Car` read through a usage of
`SportsCar :> Car` (A10-028..036, 36 cases in all). New combinations are
appended as a block so existing IDs stay stable. `run-all.sh` also writes
`results/report-all.md`.

Decisions / findings:
- Package-level `part car : Car` is isComposite=false, isReference=true in both
  the Pilot and sysml-toolkit (no owning type), so that is the expected value.
- Pilot Implementation fails under JDK 25 (Xtend, class file version 69); build
  and run it with JDK 21.
- Go suite needed `go mod tidy` for go.sum with a `replace` directive.
- The Pilot lists library-inherited features (start, done, subparts); unnamed
  counts are restricted to the declaring element for that reason.
- Unnamed parts are counted through the query API in the OpenSysML suites; the
  Symbol.children() route drops them (issue #1960) and is not what is measured.

## Step 3 (draft): plan of matrices

### Principles
- Each matrix is the full cross product of **what is read** x **where the
  element appears** x **variant of the element**, as A10 is. A matrix whose
  product becomes too large is split by variant, not thinned out.
- The location dimension is reused across matrices, since inherited items are
  where the APIs were seen to lose information:
  - L1 owned by a package
  - L2 owned by a definition
  - L3 read through a usage typed by that definition
  - L4 read through a usage of a definition that specializes it
  - L5 redefined in a usage (`:>> x = ...`), read through that usage
  - L6 reached through a feature chain of nested usages (`a.b.c`)

  Not every location applies to every matrix. The matrix states which ones apply.
- Definitions are tested as subjects in their own right, not only as containers
  of usages. Their locations:
  - DL1 owned by a package
  - DL2 nested in another definition
  - DL3 owned by a nested package
  - DL4 reached through an import or alias
  - DL5 a standard-library definition (`ScalarValues::Real`, `Parts::Part`)
- Where a usage has a definition-side counterpart, the matrix covers both sides.
  Examples: the ends of a connection def and of a connection usage, the
  parameters of an action def and of an action usage, the features of a port def
  and of a port usage.
- One model file and one generator per matrix. When the second generator is
  written, the shared parts of `gen_a10.py` move into a small common module.
- Expected values come from the specification. Where it is unclear, the Pilot
  Implementation is the oracle, and the decision is recorded here.
- Matrices that import the standard library (ScalarValues, ISQ, ...) need the
  library in every MDK. OpenSysML embeds it, and the Pilot has `sysml.library`.
  sysml-toolkit needs its `spec-refs/SysML-v2-Release` submodule initialised.

### Decisions
- **Members inherited from the standard library are counted.** For example,
  `Parts::Part` gives every part def `start`, `done`, `subparts`, ...
  Consequences:
  - Expected member lists include library members. They are derived from the
    library source, with the Pilot as the oracle, and they name the library
    version used.
  - The MDKs bundle different library snapshots. OpenSysML embeds its own,
    sysml-toolkit pins the `SysML-v2-Release` submodule, and the Pilot has
    `sysml.library`. A version difference could look like an API defect. Before
    A02, compare the library versions. Where they differ, a case is marked as
    depending on the library, so such a failure can be told apart.
  - sysml-toolkit must load the library (`spec-refs/SysML-v2-Release`
    initialised), or it cannot report library members at all.
  - The OpenSysML Python `attributes()` deliberately leaves out library
    attributes and reports only their count (`withheld_library_attributes`). Under
    this decision that counts as missing, not as unsupported.
  - A10 is unaffected: its only member-list check counts unnamed parts declared
    in the model itself.

- **Secondary routes are not probed.** Each suite reads through the MDK's main
  API only. Workarounds are not tried, and there is no outcome for "readable
  only by a workaround". The main API of each MDK:
  - OpenSysML (Python, Go): the Symbol API and the query API. Reflection
    (`eval` over metaobjects) and api-json / RDF export are not used.
    (Superseded in Step 5: the Symbol API only.)
  - sysml-toolkit: `ResolvedModel`, its semantic model. Owned properties are
    read with `element_properties` and derived ones with
    `derived(element, "<spec name>")`. (Corrected in Step 4: an earlier version
    of this note said the toolkit had no element-level API and used the
    full-form JSON export instead.)
  - Pilot Implementation: the EMF model (`org.omg.sysml.lang.sysml`).
- **B10 is split into B10 and B11**, by connector kind (see the table).
- **Other OpenSysML clients wait.** The TS, Java and Rust clients are left for a
  later time.

### Suggested order
1. A20, A30, B10, B11, C10, C20, D10: each is backed by an issue already seen in practice.
2. A01, A02, A40, A50.
3. C01.
4. A60, B20, C30, D20, E10.
5. F10 last. Only some MDKs have a runtime, so most results would be "unsupported".

## Step 4: first group of matrices

### Infrastructure changes
- Every suite now runs all of `data/cases/*.json` (one runner per suite), and the
  CSV `matrix` column tells the matrices apart. `report.py` starts with a
  per-matrix summary (pass / fail / unsupported / error for each suite).
- Generators share `data/genlib.py`. `gen_a10.py` was ported to it and produces

- A case may carry `accept`: alternative values that also count as a pass. It

  generator gives the reason.
- sysml-toolkit's library submodule `spec-refs/SysML-v2-Release` is initialised
  (pinned at de1070a, 2026-07-22). The Pilot's `sysml.library` is 0.64.0
  (2026-10-01). OpenSysML's embedded library version is still to be checked

### Correction: sysml-toolkit A10 results
The first sysml-toolkit adapter read the full-form JSON export. In that export,
`inheritedFeature` is always empty, so every inherited case failed. The toolkit's
semantic model (`ResolvedModel`) does compute inherited features, and with an
adapter on that API sysml-toolkit passes all of A10. The earlier fail results
for sysml-toolkit came from the route, not the model.

Observations kept for later matrices (A02 will test them directly):
- `ResolvedModel::derived(car, "inheritedFeature")` lists engine, driver and the
  unnamed part, but `feature`, `member` and `membership` are empty for `car`. The
  spec derives those to include inherited ones.
- That `inheritedFeature` leaves out library-inherited features (Part's `start`,
  `done`, ...). Under the Step 3 decision, those should be counted.
- In the full-form JSON export, `inheritedFeature` is empty.
- How "visible through a usage" is read: the union of an API's member listings
  (OpenSysML: `children()`, `parts()`, `attributes()`; sysml-toolkit and Pilot:
  `feature`, `ownedFeature`, `inheritedFeature`).

### A20 attribute usages
5 reads x 5 locations (L1-L5) x 4 variants = 100 cases. Reads are spec
properties taken literally (see the `notes` in `cases/A20.json`):
- name is `Element::name`, the effective name.
- type is the first of `Feature::type`, which includes types inherited through
  redefinition.
- multiplicity is `Type::multiplicity`, the owned multiplicity only. A
  redefinition without its own multiplicity expects none.
- value and isDefault come from the feature's owned `FeatureValue` membership.
  `valuation` is only an association end in KerML, so it is not used.

Decisions:
- A bound value (`= 1.5`) cannot be overridden by a redefinition
  (`validateFeatureValueOverriding`; sysml-toolkit reported it), so the L5
  "bound" variant is redefined without a value.
- For `tuned::bound`, the owned-FeatureValue reading is "no value". But the
  feature is still bound to 1.5 by the redefined feature, and the OpenSysML
  Python API reports 1.5. Both are accepted.

Findings:
- OpenSysML (Python and Go): redefining features (`attribute :>> plain = 3.5`)
  report no type. `Feature::type` should include the redefined feature's
  `Real`. There is also no way to tell a default value from a bound value
  (isDefault is unsupported).
- Pilot and sysml-toolkit pass all 100 cases.

### A30 port usages and conjugation
44 cases in two blocks:
- Reads on the port usage (name, type, typeIsConjugated) x locations (L2, L3,
  L4, L6) x typing (`CmdPort`, `~CmdPort`).
- Direction of the port def's features as seen through the port
  (`Type::directionOf`) x locations (the port def itself, L2, L3, L4, L6) x
  typing x the feature's declared direction (out `cmd`, in `ack`).

Infrastructure: `through` may now be a path (`["A30::rack", "A30::Rack::slot"]`),
so L6 reads the port through a chain of nested usages. Qualified names are
compared without quotes, because OpenSysML spells `CmdPort::~CmdPort` where the
notation quotes `CmdPort::'~CmdPort'`. The quoted form is expected and the
unquoted form is accepted.

How each MDK is read: Pilot `Type.directionOf`; sysml-toolkit the operation
`Core-Types-Type-directionOf_Feature`; OpenSysML has only the member's own
`direction` metadata. OpenSysML gives a conjugated port def the same kind as an
ordinary one (`portDef`), so conjugation is detected from the spec naming rule
(`~` + the original's name).

Findings:
- OpenSysML (Python, Go): a `~CmdPort` port reports type `CmdPort` (#1962), and
  directions seen through it are not swapped. Ports are not listed through
  typing usages, specializations or chains (#1961). The conjugated def lists no
  features.
- sysml-toolkit: the conjugated def `CmdPort::'~CmdPort'` lists no features, so
  `cmd`/`ack` are not visible through it (A30-027/028). The Pilot lists them
  with swapped directions. Everything else passes.
- Pilot: all 44 pass.

### B10 connection and interface ends
98 cases:
- 5 reads x 2 kinds (connection, interface) x 3 end depths (`q`, `x.p`,
  `m.u1.p`) x 3 locations (L2, L3, L6) = 90.
- The def side: endCount and endNames of `Link`/`Iface`, and of
  `SubLink :> Link`/`SubIface :> Iface` (inherited ends) = 8.

A referenced feature is compared in chain form: the qualified names of its
`chainingFeature`s, or `[qn]` for a feature that is not a chain. relatedFeature,
sourceFeature and targetFeature follow KerML: the ends' referenced features,
so for a chained end the chain feature, not its last feature (#1957).

Findings:
- OpenSysML (Python, Go): a connector whose ends are unnamed (`connect x.p to
  y.p`) lists no ends at all, so endCount is 0 (#1960). relatedFeature,
  sourceFeature and targetFeature are not available (#1956). End features of a
  connection/interface def have no end marker (kind `referenceUsage`), so the
  def-side reads are unsupported. Connectors are not listed through typing
  usages or chains.
- sysml-toolkit: everything on connector usages passes, chained ends included.
  A specializing def (`SubLink :> Link`) reports no `endFeature`, although it
  inherits Link's ends. This is the same pattern as `feature` leaving out
  inherited features.
- Pilot: all 98 pass.

Adapter fix found on the way: the sysml-toolkit adapter ignored element
references held in owned properties (`{"@id": ...}`). They are now resolved.

Planned addition, B12: the same reads for connectors with named ends
(`connect supplier ::> x.p to consumer ::> y.p`), as in the model of #1956.
It is kept separate so B10 stays near 100 cases.

### B11 binding connector ends
90 cases: B10's 5 reads x naming (`binding b0 bind ...`, unnamed `bind ...`) x
end depth 0/1/2 x locations (L2, L3, L6).

Scope change: flows were moved from B11 to B20. A flow end is not a plain
reference: `flow from x.o to y.i` gives an end that references `x` and owns a
flow feature redefining `o`. Its expected values need the flow-specific reads
planned for B20.

New locator: an unnamed element has no qualified name, so a case can carry
`unnamed: {metaclass, index}`. It selects the index-th unnamed member of that
metaclass declared in `element` (declaration order), visible in the last element
of `through` when one is given.

Findings:
- OpenSysML (Python, Go): a binding never lists its ends, named or not, because
  binding ends are always unnamed (#1960). Unnamed bindings cannot be found
  through the Symbol API. relatedFeature, sourceFeature and targetFeature are
  unsupported.
- Pilot and sysml-toolkit: all 90 pass.

### C10 action parameters and bound values
Decision (agreed): bound expressions are compared by structure, not text.
116 cases in two blocks:
- Value reads (valueKind = metaclass, valueOperator, valueReferences in chain
  form, valueText) x value variants (literal, feature reference, feature chain,
  operator expression, no value) x locations (perform action in part def, action
  usage in part def, through typing usage, through usage of specialized def) = 80.
- Parameter reads (name, direction, type) x direction (in, out, inout) x
  locations (action def, through specializing action def, through perform
  action, through typing usage) = 36.

valueText is unsupported where an API cannot return source text. That is so far
every MDK: OpenSysML has no expression at all, and the Pilot and sysml-toolkit
models carry no text.

Corrections found by the oracle: a FeatureChainExpression is an
OperatorExpression with operator "." (KerML), so valueOperator for
`powerPort.power` is "." (the Pilot reported it). The sysml-toolkit adapter
compared the metaclass name exactly and now uses the toolkit's
`metaclass_conforms`.

Findings:
- OpenSysML (Python, Go): no expression structure (#1965). A parameter redefined
  by `in pLiteral = 0.5` reports no type and no redefines edge. Actions are not
  listed through typing usages.
- Pilot and sysml-toolkit: all structural reads pass.

### C20 kinds of action
120 cases: 5 reads (kind = metaclass, payloadArgument, senderArgument,
receiverArgument, assignedFeature) x 8 kinds (send via, send to, accept via,
assign, perform, if, while, for) x 3 locations (action def body, nested in an
action usage in a part def, through typing usage). State entry actions are left
to C30.

Findings:
- OpenSysML (Python, Go): every kind is reported as a plain `actionUsage`
  (#1985, which here extends to accept, assign, perform, if, while and for). No
  arguments are available.
- sysml-toolkit: AssignmentActionUsage `referent` is null. Its model of
  `assign count := 1` has the `target` and `replacementValues` parameters but no
  membership naming `count`, even though `derives` reports the property as
  exactly computed. Everything else passes.
- Pilot: all 120 pass.

### D10 metadata annotations
45 cases: 3 reads (metadataDefs, metadataValue, annotatedElement) x 3 forms
(prefix `#M`, body `@M { ... }`, `metadata m : M about x` owned elsewhere) x 5
sites (part def, part usage, state, action parameter, part usage through typing
usage). The annotations of an element are the MetadataUsages whose
annotatedElement includes it, wherever they are owned. The metamodel APIs have
no navigable link from the annotated element, so they scan the MetadataUsages.

Findings:
- OpenSysML (Python, Go): no annotation is found in any form. Prefix and body
  annotations are not children (#1963). The query API lists a body annotation as
  an anonymous `@0` row with no type. A named `metadata ... about x` is a symbol,
  but nothing reports what it annotates.
- Pilot and sysml-toolkit: all 45 pass.

### First group: status
A20, A30, B10, B11, C10, C20 and D10 are done (649 cases including A10).

### B12 named connector ends
108 cases: B10 with every end named (`connect supplier ::> x.p to consumer ::>
y.p`, the form in the model of #1956). B10's 5 reads plus endNames x 2 kinds x 3
end depths x 3 locations (L2, L3, L6).

Findings:
- OpenSysML (Python, Go): named ends are listed, unlike unnamed ones (B10). So
  endCount and endNames pass when the connector is read in its part def. Each
  end's reference is missing: no subsets/references specialization is reported
  (#1956), at every end depth. relatedFeature, sourceFeature and targetFeature
  are unsupported. Connectors are not listed through typing usages or chains.
- Pilot and sysml-toolkit: all 108 pass.

With B12 the suite has 757 cases in 9 matrices.

### Versions in the report
`run-all.sh` records the version each suite ran against
(`results/<suite>.version.json`, written by `test-suite/mdk_version.py` right
after the suite runs). `report-all.md` starts with a "Versions tested" table:
MDK commit and `git describe`, commit date, standard library, the API exercised,
toolchain, run time, and the test suite's own commit. Tracked files that differ
from the MDK commit are listed. The Pilot's Maven build rewrites two committed

always shows as modified after a build.

The standard libraries differ between the MDKs: OpenSysML embeds
SysML-v2-Release 2026-09, sysml-toolkit's submodule is at 2026-05, and the Pilot
uses its own 0.64.0-SNAPSHOT library. A02 (library-inherited members) has to

## Step 5: second group of matrices

### Library comparison (before A02)
The library sources of OpenSysML (`internal/workspace/libs/stdlib`) and of the
Pilot (`sysml.library` at the tested commit) are identical; only Eclipse
project files differ. sysml-toolkit's submodule (SysML-v2-Release 2026-05)
differs from them in 14 files, among them `Kernel Semantic Library/Objects.kerml`
and `Systems Library/Actions.sysml`. A sysml-toolkit failure on a
library-inherited member is checked against this diff before it is called a
defect.

### A01 structural definitions
117 cases in two blocks:
- name, shortName and kind x 10 definition kinds (part, item, attribute, port,
  connection, interface, allocation, enum, occurrence, metadata) x 3 locations
  (owned by a package, nested in a part def, in a nested package) = 90.
- name, kind and isAbstract of the standard-library definition of each kind
  (`Parts::Part`, `Items::Item`, ...; the library has no SysML occurrence def) = 27.

Reads through an import or alias are left to A60. isVariation and isIndividual
go to a new matrix A03, to keep A01 near 100 cases.

Decisions:
- A connection or interface def without ends is invalid. The Pilot and OpenSysML
  both report "Must have at least two related elements"; sysml-toolkit's `check`
  accepts it (observation, not a test case). The model gives them two ends.
- An enumeration def is a variation, and a variation def is abstract, so
  `VerificationCases::VerdictKind` is expected abstract. All three MDKs agreed
  with this before the expected value was corrected.

Adapter changes: the OpenSysML adapters read kind (the exact `@type`), shortName
and isAbstract from the query API. The Symbol API has no short name, and its kind
is an abbreviation (`partDef`). The Pilot adapter now also looks up elements in
the library resources.

Findings:
- OpenSysML: the query API reports `VerdictKind` with isAbstract false, while
  its Symbol metadata says `abstract: true`. Everything else passes.
- Pilot and sysml-toolkit: all 117 pass.

### A02 definition specialization
50 cases: 5 reads (directGenerals, allSupertypes, ownedFeatureNames,
inheritedFeatureNames, redefinitions) x 5 definitions (no explicit general;
`Mid :> Base`; `Leaf :> Mid` with a redefinition; `Multi :> Base, Other`;
`FromAbs :> abstract AbsBase`) x 2 locations (package, nested package).

Decisions:
- allSupertypes is `Type::allSupertypes()` =
  `OrderedSet{self}->closure(supertypes(false))`. Whether an OCL closure
  contains its source is read both ways: the Pilot (Eclipse OCL) leaves the type
  out, and sysml-toolkit includes it. The Pilot's form is expected and the form
  with the type is accepted.
- inheritedFeatureNames counts library members (Step 3 decision). Their list is
  the Pilot's answer (library 0.64.0: 71 named features and 18 unnamed ones
  inherited through Parts::Part), and every name was checked to be declared in
  Parts.sysml, Items.sysml, Objects.kerml, Occurrences.kerml or Base.kerml.
  These cases carry `libraryDependent: true`.

Findings:
- OpenSysML (Python, Go): direct generals, owned features and redefinitions
  pass. No supertype closure is available (unsupported). Inherited features
  come only from `attributes()`, so inherited parts are missing (#1961), and
  library members are withheld (`withheld_library_attributes`).
- sysml-toolkit: everything passes except inheritedFeatureNames. It returns the
  features inherited from definitions in the model, but none of the library's.
  The toolkit's own library defines those features, so this is not a library
  version difference. `inheritedFeature` follows only explicit specializations,
  not the implied `Parts::Part`.
- Pilot: all 50 pass.

### A40 specialization relations of usages
45 cases: 3 reads (specializations as [metaclass, general] pairs,
subsettedFeatures, types) x 5 relations (typing `: T`, subsetting `:> q`,
reference subsetting `::> q`, typing and subsetting `: V :> q`, redefinition
`:>> q`) x 3 locations (L2, L3, L4). Implied relationships (every part usage
subsets `Parts::parts`) are left out.

Adapter fix: each kind of Specialization redefines `general`, and a
Subsetting's `subsettedFeature`, under its own name (`type`, `redefinedFeature`,
`referencedFeature`, `superclassifier`). sysml-toolkit answers only to that
name, so the adapter reads the property that applies to the metaclass. Its first
failures here were caused by the adapter, not the toolkit.

Findings:
- OpenSysML (Python, Go): reference subsetting `::> q` is not reported at all.
  `type` is the declared type only: a feature typed through subsetting or
  redefinition reports none, and `: V :> q` reports V without q's T. Usages are
  not listed through typing usages or specializations (#1961). Typing,
  subsetting and redefinition read in the part def pass.
- Pilot and sysml-toolkit: all 45 pass.

### A50 unnamed members
54 cases: 3 reads (kind, owner, idRoundTrip) x 6 unnamed members (part,
attribute, `bind`, `connect`, `flow`, body metadata `@M;`) x 3 locations
(package, part def, through a typing usage of the part def). Each member is

### Decision: OpenSysML is read through its Symbol API only
This supersedes the Step 3 decision that counted both OpenSysML's Symbol API and
its query API as its main API.

Background: the Symbol API is OpenSysML's own. It is one gRPC message,
`SymbolInfo` (`api/proto/sysml.proto`), and every language binding (Python, Go,
Java, Rust, ...) wraps the same fields: id, name, kind, a `metadata` map, child
ids, attributes, type facts, multiplicity and specializations. The query API
implements the OMG SysML v2 API & Services Query standard. The Pilot and
sysml-toolkit are read through their element APIs (EMF, `ResolvedModel`). The
Symbol API is OpenSysML's equivalent, and OpenSysML is free to extend
`SymbolInfo`. Taking values from the query API where the Symbol API has none
would hide gaps that a user walking the model through Symbols would hit.

Rule: every value comes from the Symbol API. When it has no field for a read, the
result is unsupported, and the detail says whether the standard query API offers
the property ("no Symbol field for the short name; available through the
standard query API (shortName)"). The query API is consulted for that note only.
Spelling translations of a Symbol field are allowed, as for Specialization
kinds: the kind `partDef` is read as `PartDefinition` (`Def` -> `Definition`,
`enum` -> `Enumeration`).

Results that changed (OpenSysML, Python and Go alike):
- A01 shortName (30 cases): pass -> unsupported (no Symbol field; the query API
  has it). A01 kind still passes, from the Symbol kind.
- A01-116 isAbstract of `VerdictKind`: fail -> pass. The Symbol metadata says
  `abstract: true`; the query API said false.
- A10-025..027 unnamedPartCount: pass -> fail. `children()` drops unnamed
  members (#1960); before, the query API listed them.
- A50 owner: no Symbol field, but these cases fail earlier, because the unnamed
  member cannot be found.
- D10 metadataDefs: the query fallback no longer applies; it had found nothing
  anyway.
- Unsupported details for isComposite, isReference, sourceFeature, targetFeature
  and relatedFeature now say that the query API does not offer them either.

## Step 6: third group of matrices

### A60 namespaces: imports, aliases and visibility
32 cases: 2 reads (resolve, referenceTarget) x 8 access paths (own member,
alias, membership import, namespace import, recursive import `::**`, private
import, private member, protected member) x 2 element kinds (a part def, reached
by a usage typed by it; an attribute, reached by an attribute subsetting it).

- resolve: the element a qualified path resolves to, or null when the path is
  not visible from outside. For the Pilot and sysml-toolkit this is KerML
  `Namespace::resolve` of the rest of the path, called on the matrix's root
  package. OpenSysML's Symbol API has one name lookup, `get(qualified name)`,
  which is given the whole path.
- referenceTarget: what a reference written through the path resolves to in the
  model (the type of `part pAlias : Lib::PumpAlias;`, the subsetted feature of
  `attribute aAlias :> Lib::rateAlias;`). References to private and protected
  paths are written where they are visible.

Observations on the way:
- (Retracted in E10.) It first looked as if the Pilot's `resolveGlobal` and
  root-level `resolve` found no top-level package of the user's document. The
  cause was the test loader: it did not enter documents in the Pilot's global
  index, as `process()` does. With that fixed, root-level resolution gives the
  same answers as `A60.resolve(...)` for all 16 resolve cases. The read keeps
  resolving from the root package.
- Adapter fix: an OwningMembership redefines `memberElement` as
  `ownedMemberElement`. sysml-toolkit answers only to the redefining name (as in
  A40).

Findings:
- OpenSysML (Python, Go): every referenceTarget passes, so references written
  through aliases, imports and visibility rules resolve correctly in the model.
  `get` is a lookup by declared qualified name, not name resolution: an alias
  gives the alias itself instead of its target, re-exported imports are not
  followed, and private and protected members are returned regardless of
  visibility. Go and Python differ: Go's in-process lookup follows a public
  namespace import (`FacadeAll::Pump`), the Python client over gRPC does not.
- Pilot and sysml-toolkit: all 32 pass.

### B20 flows
75 cases in two blocks:
- 5 reads (kind, payloadTypes, endReferences, sourceOutput, targetInput) x 2
  kinds (`flow`, `succession flow`) x 2 end depths (`tank.fuelOut`,
  `m.tank.fuelOut`) x 3 locations (L2, L3, L6) = 60.
- The 5 reads x a `message of Sig from tank to engine` x 3 locations = 15.

Flow-end structure (KerML FlowEnd, the reason flows left B11): `from
tank.fuelOut` gives an end whose ReferenceSubsetting references `tank` (the
chain before the last name) and which owns a flow feature redefining `fuelOut`.
sourceOutput and targetInput read the feature that `Flow::sourceOutputFeature` /
`targetInputFeature` redefine.

Decisions from the model and the grammar:
- A flow end must name a participant with dot notation
  (`validateFlowEndSubsetting`; sysml-toolkit reported it), so flows have no
  end depth 0.
- A message's `from tank to engine` are not connector ends.
  `MessageEventMember` returns a ParameterMembership owning an
  EventOccurrenceUsage that references `tank`/`engine`. So a message's ends
  reference nothing and own no flow feature. The Pilot follows this; my first
  expectation (ends referencing tank/engine) was wrong and was corrected.

Findings:
- OpenSysML (Python, Go): a succession flow is reported as a plain FlowUsage.
  Payload type, source output and target input are unsupported (no Symbol
  field; the query API does not offer them either). End references are missing,
  and flows are not listed through typing usages or chains.
- sysml-toolkit: flows pass, at both end depths. For a message it reports
  source and target output features redefining `tank`/`engine`: it models the
  message events as flow features, where the grammar makes them event-occurrence
  parameters.
- Pilot: all 75 pass.

- substates, isParallel x a sequential and a parallel state = 12.

## Step 7: sysml-toolkit reader modes and closure policy

Prompted by a report from another environment (sysml-toolkit v0.11.3, closure
policy with implied heritage): `PortUsage.portDefinition` and `type` refused on
all 269 ports tested ("incomplete derivation"), while the compatibility value,
effective port features and direction reads worked. The suite had not seen it
because the adapter reads derived properties through `derived`.

### Two readers
sysml-toolkit offers two readers over `ResolvedModel`:
- compatibility, `derived(element, name)`: answers a value even when its
  derivation is incomplete (for many properties, the owned side only);
- checked, `property(element, name)`: answers only a value it can certify,
  and refuses otherwise. The toolkit's strict export uses it.

Both are main APIs, so both are run, as two suites from the same crate:
`sysml-toolkit-rs` (compatibility, as before) and `sysml-toolkit-rs-checked`.
A refusal by the checked reader is recorded as `error`, as a `NotComputed`
answer of the compatibility reader already was.

### Closure policy
`ResolvedModel` defaults to the passthrough closure policy: inherited, imported
and implied-library members are left out of the inheritance-aware properties.
The specification includes them, and the other MDKs have no such switch, so
both suites now set `ClosurePolicy::Closure { include_implied: true }`. The
checked reader also refuses most type-dependent reads without it.

Effect on the compatibility suite: 43 cases changed from fail to pass and none
changed the other way (A02-031..040, the members inherited from the implied
`Parts::Part`; A50-018/036/054; B10-092/094/096/098; 26 C01 cases). The
earlier failures came from the adapter's setting, not the toolkit.

### Findings (checked reader)
1071 pass, 437 error (all refusals), 50 unsupported, no fail: every value the
checked reader gives is right.
- A30: `type` (A30-009..016) and so `typeIsConjugated` (A30-017..024) refused
  on every port usage, with or without conjugation. `type` on attribute, part
  and other usages answers. This reproduces the report above.
- B10, B11, B12 (connectors, all cases): `connectorEnd`, `sourceFeature`,
  `targetFeature` and `relatedFeature` refused.
- B20 (60 of 75): flow `payloadType`, `sourceOutputFeature`,
  `targetInputFeature` and the ends.
- C01 (36 of 96), C10, C20, C30, D10: `directedFeature`, `result`,
  `argument`, `subjectParameter`, `endFeature`, `metadataDefinition`,
  `referent`, `payloadParameter`.
- 20 cases pass under the checked reader and not under the compatibility one:
  18 A03 `isIndividual` cases between A03-065 and A03-088 (definitions that
  do not write `individual`: the checked reader fills the declared default
  `false`, the compatibility reader answers null), and A30-027/028 (the directions read
  through `CmdPort::'~CmdPort'`, whose features the compatibility reader does
  not list).
